# API를 싱가포르로 옮긴다 — 절차서

**2026-09-11 대표 승인(승인 B · 리전 이전).** 이 문서는 **절차서**다. 실행은 MASTER와
대표님이 하고, 작성 시점에 Render 대시보드를 건드린 것은 없다.

---

## 0. 순서가 먼저다 — 고지가 이전보다 앞선다

개인정보보호법 제28조의8은 **국외 이전 자체를 금지하지 않는다. 고지 없이 이전하는 것을
금지한다**(`docs/AI_HANDOFF.md:69`). 서버를 먼저 옮기고 처리방침을 나중에 고치면 그
사이가 **미고지 이전 구간**이 된다.

    ① 처리방침 개정 · 시행      ← 여기가 끝나기 전에 ②를 시작하지 않는다
    ② 싱가포르 서비스 생성 · 전환
    ③ 옛 서비스 정리

처리방침 13항이 「시행일, 변경 내용과 사유를 서비스에서 알린다」고 이미 적어 뒀다. 그
절차를 그대로 쓴다. 시행일은 `LEGAL_PRIVACY_EFFECTIVE_ON`(`infra/render-env.yml` ·
Render 대시보드) 값이고 **날짜는 대표님이 정한다.** 지금 값은 두 문서 모두
`2026-09-10`이다.

**2026-09-11 대표 결정으로 ①의 방침 수정은 끝났다**(PR #208 — 「일단 바꾸고 고지한다」).
남은 것은 시행일을 정하는 것과, **그 날짜까지 ②를 끝내는 것**이다. 자세한 것은 §7.

---

## 1. 왜 지금이 가장 싼 때인가

**설치된 앱이 세상에 없다.** 릴리즈 프로덕션 빌드는 대표님이 「완료」라고 말할 때까지
보류 중이고, 스토어에 올라간 판이 없다. 그래서 지금은 **API 주소가 바뀌어도 깨질 것이
없다** — 주소를 아는 것은 이 저장소와 Render·EAS 설정뿐이고, 둘 다 우리가 고칠 수 있다.

출시 뒤에 옮기면 다르다. 구버전 앱은 자기 번들에 박힌 옛 주소를 계속 부르고, 그 앱을
지운 사람만 새 주소를 본다. 그때는 옛 주소를 프록시로 살려 두는 일이 추가로 생긴다.

## 2. 왜 옮기는가

성능 세션(`claude/perf-audit` · PR #206)이 실측한 값이다. **이 브랜치에는 그 문서가 아직
없어서**(`docs/perf/measured.md`는 main 미반영) 여기서는 인용으로 적는다 — 이 절차서를
쓰면서 다시 측정한 값이 아니다.

    GET /        DB를 한 번도 안 봄     37ms
    GET /health  DB에 두 번 물음       436ms
                 차이 399 ÷ 2 = DB 왕복 1회 약 199ms

업체 상세 1,049ms 중 API가 일한 시간은 37ms고 나머지는 DB 왕복 5회다. **API는 원인이
아니다. 배치가 원인이다.**

    사용자(한국) ──태평양──> API(Render Ohio, 미 동부) ──태평양──> DB(Neon 싱가포르)

리전 출처: Render Ohio(US East) · Neon AWS Singapore 모두
`docs/INFRA_ACCESS_AUDIT_2026-09-10.md`의 콘솔 확인값이다. **접속 문자열은 열지 않았다** —
두 리전은 문서에 이름으로 적혀 있다.

API를 싱가포르로 옮기면 두 구간이 함께 짧아진다. API↔DB는 같은 도시가 되고, 사용자→API도
태평양을 건너지 않는다. **이전 후 값은 다시 측정한다** — 여기에 기대치를 숫자로 적지 않는다.

## 3. 먼저 확인한 것

| 확인 항목 | 결과 | 출처 |
| --- | --- | --- |
| Render는 만든 뒤 리전을 바꿀 수 있는가 | **없다.** 새 서비스를 만들어 옮겨야 한다 | Render Docs — Regions / 커뮤니티 마이그레이션 문서 |
| 그래서 주소가 바뀌는가 | **바뀐다.** 새 서비스는 새 `*.onrender.com` 슬러그를 받는다 | 위와 같음 |
| Render에 싱가포르 리전이 있는가 | 있다(oregon · ohio · virginia · frankfurt · **singapore**) | Render Docs — Regions |
| free 플랜이 싱가포르를 지원하는가 | 지원한다. 승인 C(유료 인프라)는 걸리지 않는다 | Render Docs — Regions / 요금 문서 |

**확인 필요(아직 모르는 것).**

- Render 싱가포르가 어느 클라우드·어느 AZ인지는 Render가 공개하지 않는다. 둘 다
  싱가포르지만 **같은 AZ라는 보장은 없다.** 왕복 시간은 이전 후 실측으로 확인한다.
- free 인스턴스는 15분 무요청이면 잠들고 깨는 데 시간이 걸린다. 이것은 리전과 무관한
  기존 조건이며(`docs/INFRA_ACCESS_AUDIT_2026-09-10.md`) 이번 이전으로 달라지지 않는다.

## 4. 이전 절차

### 4-0. 처리방침 먼저 (선행 조건)

1. **5항 Render 행을 「싱가포르」로 고친다 — PR #208에서 했다.** 시험이 네 행의 리전을
   각각 잠근다(`apps/web/src/legal-pages.test.ts`).
2. 대표님이 개정 시행일을 정한다. §7의 제약을 먼저 본다 — **그 날짜까지 이전이 끝나야 한다.**
3. `infra/render-env.yml`의 `LEGAL_PRIVACY_EFFECTIVE_ON`을 그 날짜로 고친다(웹사이트
   블록과 운영 API 블록 **둘 다** — 두 값이 다르면 앱과 웹이 서로 다른 시행일을 말한다).
4. main에 머지해 웹이 실제로 새 방침을 그리는지 확인한다. **여기까지가 끝나야 4-1로 간다.**

### 4-1. 싱가포르 서비스 생성

운영 API(`weddingpickl.onrender.com`)는 **이 저장소의 Blueprint 밖에서 대시보드로
관리된다**(`render.yaml:158`). 그래서 새 서비스도 대시보드에서 만든다.

- region: **Singapore** / runtime: Docker / `Dockerfile` · context `.` / healthCheckPath `/health`
- plan: free (지금과 같음)
- 환경변수는 **손으로 넣지 않는다.** 대시보드에서 서비스를 만든 뒤
  `infra/render-env.yml`에 새 서비스의 **대시보드 표시 이름**을 추가하면
  `render-env-sync`가 밀어넣는다. 이름이 글자 하나라도 다르면 그 서비스만 조용히
  건너뛰고 워크플로가 `exit 1`로 끝난다(`infra/render-env.yml:22`, `main.yml:188`).
- 비밀값(`DATABASE_URL` · `ANTHROPIC_API_KEY` · S3 자격 등)은 GitHub Secrets에서 같은
  이름으로 간다. **이 문서에 값을 적지 않는다.**
- `NODE_ENV=production`이면 `STORAGE_DRIVER=s3`와 `S3_BUCKET`이 강제된다
  (`apps/api/src/config.ts`). NCP Object Storage는 **한국**이고 그대로 둔다 — 이번에 옮기는
  것은 API뿐이다.

### 4-2. 확인

옛 서비스를 그대로 둔 채 새 서비스에서 확인한다.

- **`/health` 본문을 읽어 어느 DB를 쥐었는지 확인한다.** Live는 「프로세스가 살아 있고
  헬스체크가 200을 받았다」까지고 DB가 맞는지는 말해 주지 않는다.

  2026-09-11에 실제로 걸렸다. 새 서비스가 Live인 채로 **39개 밀린 DB**를 보고 있었다
  (적용 73 · 기대 112, 같은 시각 운영은 115 · 밀린 것 없음). 원인은 **환경변수 그룹의
  `DATABASE_URL`이 `weddingpick_staging`을 가리킨 것**이었고, **호스트는 같고 `/` 뒤의
  데이터베이스 이름만 달랐다.** 눈으로 훑어서는 안 보이는 차이다.

  고치는 법은 **서비스 레벨에 `DATABASE_URL`을 따로 넣어 그룹 값을 덮는 것**이다.
  **그룹 값은 고치지 않는다** — 다른 서비스가 staging을 일부러 볼 수 있다.

  `api-health` 워크플로가 주소를 입력으로 받으므로 사람이 로그를 훑지 말고 그것으로 판정한다.

  **남은 확인:** 환경변수 그룹 「웨딩픽」에 붙은 **다른 서비스들도 staging을 보고 있는지.**
  이사와 무관하게 이미 있던 위험이다
- 카카오 로그인이 끝까지 도는가(§6 참조 — 콘솔 등록이 필요한지 먼저 판단한다)
- 업체 상세 응답 시간을 **실측**한다. 이전 전 값과 나란히 적는다.

### 4-3. 전환

저장소의 주소를 새 주소로 바꾸고(§5) main에 머지한다. `main`에 머지하면 곧바로
운영이다(Render 세 서비스가 `branch=main` · `autoDeploy=yes`). **미리 볼 스테이징이
없다는 것을 알고 머지한다.**

## 5. 갈아끼울 자리 — 저장소 안(14개 파일 · 36곳)

**먼저 한 가지를 확인하고 시작한다.** 이 장은 「주소가 바뀐다」를 전제로 한 목록이고,
주소를 지킬 수 있으면 **한 줄도 고칠 필요가 없다.**

> **확인할 것: 새 서비스가 옛 주소를 물려받을 수 있는가.**
>
> PR #206이 「임시 이름으로 만들어 확인한 뒤 이름을 바꿔 끼우면 주소가 그대로」라고
> 적었다. 그게 되면 이 장 전체가 필요 없어지므로, **§4-1로 가기 전에** 판정한다.
>
> 판정 방법은 대시보드에서 서비스 하나의 이름을 바꿔 보고 주소가 따라가는지다.
> 되돌리기 쉬운 조작이고 5분이면 끝난다.
>
> **지금까지 모은 것은 「안 된다」 쪽이다.**
> - `infra/render-env.yml:40`이 「표시 이름과 주소의 슬러그(`weddingpick-admin.onrender.com`)는
>   **다른 값**이라는 데 주의한다」고 적어 뒀다 — 이 저장소의 서비스들은 이미 이름과 주소가
>   따로 논다. 이름을 바꿔도 주소는 안 따라간다는 뜻이다.
> - Render 커뮤니티에 서비스를 지운 뒤 같은 주소로 새로 만들려다 「URL이 사용 중」으로
>   거부당한 사례가 있다(「Reusing Old URL」 · 「Domains Blocked by Deleted Service」).
>
> **다만 공식 문서로 확정하지 못했다**(작성 당시 컨테이너에서 `render.com` 송신이 막혔다).

## 6. 우리 손 밖에 있는 것 — 대표님 몫

| 자리 | 이번 이전으로 바뀌는가 |
| --- | --- |
| Render 대시보드 — 새 서비스 생성, 리전 선택, free 플랜 | **필요하다** |
| GitHub Secrets — 새 서비스 이름으로 환경변수 동기화가 닿는지 | 필요하다(값 변경은 없음) |
| EAS(`eas.json`) 빌드 프로필의 `EXPO_PUBLIC_API_URL` | 저장소 쪽이라 §5에 포함 |
| **카카오 개발자 콘솔 — Redirect URI** | **바뀌지 않는다.** 웹 로그인의 redirect URI는 `window.location.origin`에서 만든다(`apps/mobile/src/features/auth/providers.ts:80`) — 즉 **앱 웹 호스트**(`weddingpick-app-web.onrender.com`)이지 API 호스트가 아니다. 이번에 앱 웹은 옮기지 않으므로 콘솔 등록은 그대로다. **앱 웹까지 옮기기로 하면 그때는 필요하다.** |
| 네이버 개발자 콘솔 | 해당 없다 — 네이버 로그인은 폐기됐다(v3.12, 카카오만 남음) |
| 운영 API의 `CORS_ORIGINS` | 바뀌지 않는다. 목록에 든 것은 API를 **부르는** 세 웹 출처이고 API 자기 주소가 아니다 |
| **서비스 이름 바꾸기로 주소를 물려받을 수 있는지 판정** | **필요하다** — §5 맨 위. 대시보드에서 5분. 이 판정이 §5 전체를 켜고 끈다 |

**주소를 지킬 수 있는 것으로 판정되면** 위 표에서 바뀌는 것은 「새 서비스 생성」 하나뿐이고
§5는 통째로 건너뛴다. 카카오 콘솔은 어느 쪽이든 그대로다 — redirect URI가 애초에 API 주소를
가리키지 않기 때문이다.

## 7. 처리방침은 이미 바꿨다 — 시행일까지 이전을 끝낸다

**2026-09-11 대표 결정: 「일단 바꾸고 고지한다」.** 예고 단계를 두지 않는다. 5항 Render 행을
곧장 「싱가포르」로 바꾸고 그 개정을 시행일과 함께 알린다(PR #208).

    처리방침 개정 · 시행      ← 먼저. 이미 바꿨다
    서버 이전                ← 시행일까지 끝낸다
    옛 서비스 정리

**고지가 이전보다 앞서므로 미고지 이전 구간은 생기지 않는다.** 대신 반대 방향의 구간이
생긴다 — **시행일부터 실제 이전이 끝날 때까지 방침이 사실보다 앞서 있다.**

그래서 이 절차서의 제약은 하나로 줄어든다.

> **시행일까지 API가 싱가포르에 있어야 한다.**

시행일을 잡을 때 §4의 작업 시간을 먼저 본다. 새 서비스 생성 · 환경변수 동기화 · 확인 ·
주소 교체 · 머지가 다 들어가는 날짜여야 한다. 이전이 늦어질 것 같으면 **서버를 서두르지
말고 시행일을 미룬다** — 방침과 사실이 어긋난 채로 두는 것이 더 나쁘다.

시행일은 `LEGAL_PRIVACY_EFFECTIVE_ON`이고 **대표님이 정한다**(`infra/render-env.yml`의
웹사이트 블록과 운영 API 블록 **둘 다**). 다르게 넣으면 앱과 웹이 서로 다른 시행일을 말한다.

**Anthropic과 Expo는 미국 그대로다.** 넷을 싱가포르로 뭉뚱그리지 않는다 — 옮기는 것은
API 하나다. `apps/web/src/legal-pages.test.ts`가 네 행을 각각 잠근다.

## 8. 되돌리는 길

- **옛 서비스를 바로 지우지 않는다.** 새 서비스가 운영을 받기 시작한 뒤에도 그대로 둔다.
- 되돌릴 때는 §5의 주소를 옛 주소로 되돌리고 main에 머지한다. 옛 서비스가 살아 있는 한

- **지우는 시점:** 새 주소로 `api-health` 워크플로가 연속으로 초록이고, 대표님이 스토어
